# レイアウトの型

「このスライドは何をする枚か」を決めてから、対応する型を選ぶ。
主張と証拠を選んでから、その見せ方として型を選ぶ。写真・実画面・結果表も主視覚になる。
この文書は版面の参考集であり、すべてを図解する義務や、特定の体言止め・対称比率の義務ではない。

---

## 1. 拠って立つ原則

出典のあるものだけを置く。思いつきの美学は入れない。

| 原則 | 何を言っているか | 出典 |
|---|---|---|
| **Assertion–Evidence** | 主張と視覚的証拠を 1 対 1 に対応させる。本文では証拠が支える具体的な主張を見出しにする。名称だけで意味が決まる紹介・節扉は短い題でよい | Michael Alley, Penn State |
| **一貫性（coherence）** | 主題に不要な語・図・装飾は、あるだけで理解を下げる | Richard Mayer, マルチメディア学習の原則 |
| **冗長性（redundancy）** | 同じ文をスライドに出しながら読み上げると、読む処理と聴く処理が競合して両方落ちる | 同上 |
| **空間的近接（spatial contiguity）** | ラベルは対象の隣に置く。凡例や脚注に飛ばさない | 同上 |
| **シグナリング（signaling）** | どこが要点かを 1 つだけ目立たせる。全部強調は無強調と同じ | 同上 |
| **分割（segmenting）** | 一度に渡す量を切る。1 枚に詰めるより枚を割る | 同上 |
| **グリッドシステム** | 版面をカラムとフィールドに割り、全要素をその線に載せる | Müller-Brockmann『Grid Systems in Graphic Design』1981 |
| **CRAP** | Contrast / Repetition / Alignment / Proximity の 4 点で検査する | Robin Williams |
| **ゲシュタルト** | 近接・類同・共通領域・連続。CRAP の根拠側 | — |
| **データインク比** | 情報を運ばないインクを削る。枠・網掛け・影は基本いらない | Edward Tufte |
| **メッセージ → 比較の型 → チャート** | 言いたいことが決まると図の種類は機械的に決まる | Gene Zelazny『Say It With Charts』 |
| **ピラミッド** | 結論を先に、下に MECE な根拠 | Barbara Minto |

**Mayer の冗長性の原則が、日本の資料でいちばん破られている。**
スライドに書いた文をそのまま読み上げると、聞き手は読むのをやめるか聴くのをやめる。
スライドに置くのは「読ませる文」ではなく「見せる証拠」。話す言葉は別に用意する。

## 2. 密度の目安

以下はローカルな編集の目安。Mayer等が指定した文字数ではない。
判型・投影距離・配布用かで調整し、スクショ内の密度は別にPNGで確かめる。

| 区分 | 本文の文字数 | 段落数 |
|---|---|---|
| Statement（表紙・扉・命題・締め） | **40 字以下** | 1〜5 |
| 通常の内容枚 | **100〜150 字** | 8〜12 |
| 一覧・カタログ枚（許容の上限） | **300 字** | 20 前後 |
| これを超えたら | **枚を割る**。詰めるのではなく分ける | — |

実測の取り方（PowerPoint の中身をそのまま数える）：

```python
txts = [("".join(r.text or "" for r in p.iter(A+"t"))).strip() for p in root.iter(A+"p")]
chars = sum(len(t) for t in txts if t)
```

## 2.5 縦のグリッド（ここを飛ばすと「崩れて見える」になる）

Müller-Brockmann のグリッドは**列と行の両方**を指す。列（`col()`）だけ実装して縦を
目分量で置くと、1 枚ごとにブロックの間隔が変わり、めくったときに要素が跳ねる。
**文字量が予算内でも崩れて見えるときは、たいてい原因はこれ。**

行の単位を 1 つ決め、**全ブロックをその倍数に置く**。

```python
ROW = inches(0.28)          # 本文 13pt × 行送り 1.55 ≒ 1 行ぶん
rule(s,  X, top,              CW, LINE_STR)   # top + ROW*0
body(s,  X, top + ROW * 0.6,  ...)            # top + ROW*0.6
rule(s,  X, top + ROW * 2.2,  CW, LINE)       # top + ROW*2.2
arch(s,  X, top + ROW * 3.2,  CW, spec)       # top + ROW*3.2
```

やってはいけない置き方（実際にこれで崩れた）:

```python
dtag (s, lx, top + inches(0.02), ...)   # 0.02
rule (s, lx, top + inches(0.34), ...)   # 0.34
body (s, lx, top + inches(0.86), ...)   # 0.86
verse(s, lx, top + inches(2.06), ...)   # 2.06   ← 共通の単位が無い
dtag (s, lx, FOOT_Y - inches(0.62), ..) #        ← 基準が top から FOOT_Y に変わる
```

**基準点を途中で変えない。** 上から積むブロックは全部 `top` 基準、
下端に貼りつけるものだけ `FOOT_Y` 基準にして、その 2 つを混ぜない。

**繰り返すセルの内部は、この倍数でなくてよい。** カードやノードの中の
アイコン・名前・説明の間隔は、全セルで**同一**でありさえすればいい。
ページ直下のブロックと、セル内部のリズムを混同しない。

### 下端は「引き算」でなく「積み上げ」で決める

```python
ay = min(top + ph + row(5.8), FOOT_Y - row(2.5))   # ✗ 目分量 ＋ 頭打ち
```

これは、説明が 1 行のうちは通るが、**行数が増えた月に本文へ載る**。
`min()` が発火した瞬間に基準が `top` から `FOOT_Y` にすり替わり、
上のブロックとの間隔が保証されなくなる。積み上げて算出する。

```python
desc_h = max(est_height([ln], cw, 13, 1.7) for _, _, ln in PILLARS)
ay = top + ph + row(2.8) + desc_h + row(1)          # ✓ 中身から決まる
```

`FOOT_Y` からの引き算は、**上に何も無いブロック**（締めの 1 行、連絡先）にだけ使う。

列を 2 つに割るときは、**両方の列が同じ行に乗っているか**を必ず確かめる。
片方だけ別のリズムで動いていると、割った意味が消えて散らかって見える。
乗らないなら列を割らず、**全幅 1 段**にするほうがきれいに決まる。

## 2.6 重心と情報のまとまり

型も行グリッドも守っているのに「崩れている」「ダサい」と言われる枚がある。
重心やまとまりを確認する。以下は典型例で、唯一の原因や固定の個数制限ではない。

### (a) ブロックが 4 つ以上ある

まず2〜3のまとまりで要点を示せるか考える。数が増える場合は、読む順序と各ブロックの役割が明確か確認する。

```
✗  左上に数字、左下に説明、中央に棒、右に空白、下にアイコン、右下に URL
   → 6 ブロック。視線の起点が無い

✓  左＝データ（棒）｜ 右＝結論の数字 ｜ 下＝人
   → 3 ブロック。左上から右へ、最後に下へ落ちる
```

数え方：**罫線や余白で切れて見えるまとまり**を 1 ブロックと数える。
まとまりが増えて要点を追えない場合は、不要なものを落とすか枚を割る。

### (b) 片側が空いている

片側に要素が集まっていても、余白が視線を主視覚へ導くなら問題ない。
主視覚が小さく片隅へ寄って理解を妨げる場合は、拡大・中央寄せ・分割比率の変更を試す。

- 空いている側へ、主張に不要な数字・写真・説明を追加しない。
- 大きい数字には対象・単位・母数等、意味が決まるラベルを残す。
- 中心を合わせる場合は、テキストボックスの枠だけでなく描画された文字・画像の重心も見る。

### 大きな級数を中心に合わせるときの実務

級数 100pt を超えると、行送り 1.0 でもベースラインが深く、
**テキストボックスの上端とグリフの上端が 1 インチ近くずれる**。
`est_height` は行数しか見ないのでここでは使えない。
一度レンダリングして**グリフの実測位置で合わせ直す**。

```python
# 120pt は行送り 1.0 でもベースラインが深いので、実測した位置で中心に合わせる
_, tf = textbox(s, nx, center - inches(1.5), nw, inches(1.9))
```

## 3. 型の選び方

「この枚は何をするのか」から入る。

| その枚の目的 | 選ぶ型 |
|---|---|
| 章の切れ目を示す | **A. ディバイダー** |
| 1 つの言葉で温度を上げる | **B. ステートメント** |
| 主張を 1 つ立て、証拠を添える | **C. 非対称 2 分割** |
| 並列な 3 つを見せる | **D. 3 カラム** |
| 同種のものを全部見せる | **E. グリッド** |
| 数字を 1 つ立てる | **F. データコールアウト** |

## 4. 型の定義

### A. ディバイダー
```
■■■■■■■■■■■■■■■■■■■■■■■■  ← 面ごと反転（ink）
   I     やっていること
■■■■■■■■■■■■■■■■■■■■■■■■
```
- 面を反転する。章の切れ目が一目で分かり、色のリズムも生まれる
- **置くのは数字と章名だけ。** 説明文を足すとメタ text になる
- 数字は 90pt 以上。ここで級数の段の頂点を作る
- 尺は 10 秒。読み上げない

### B. ステートメント
```
検証できる社会のために、
住んで研究しています。          ← 34〜132pt
```
- 1 枚 1 文。本文は置かないか 1 行
- **余白が主役。**埋めない
- 表紙・締め・中心命題で使う。反転面と相性がいい

### C. 非対称 2 分割（5:7 / 4:8）
```
┌──────┬──────────────┐
│ 題・数字 │  [主視覚：写真・図・スクショ]  │
│ 数字 │                             │
└──────┴──────────────┘
```
- 主視覚と短い要点なら5:7等の非対称を使える。対等な比較では6:6も選べる。
- 左に要点、右に主視覚など、読む順序を決める。必要な一文は残し、長い説明で埋めない
- 原文引用等の文字が証拠なら、出所と読ませたい範囲を明確にする。

### D. 3 カラム
```
[写真]      [写真]      [写真]
名札        名札        名札
1 行        1 行        1 行
```
- **3 が上限。** 2 は対比に見え、4 以上は一覧になる
- 各カラムの文字は名札 1 語 ＋ 1 行まで
- 写真は**全部同じ比率**に。違うと不揃いに見える

### E. グリッド（n×m カタログ）
```
─────   ─────   ─────   ─────   ─────
[icon]  [icon]  [icon]  [icon]  [icon]
名前    名前    名前    名前    名前
────    ────    ────    ────    ────
説明    説明    説明    説明    説明
```
- 在庫を見せる型。**セルの型を完全に統一する**
- 名前の級数を文字数で変えない。揃っていないだけに見える
- **枠で囲わない。**上端の罫線 1 本で十分（Tufte のデータインク比）
- 2 行になる名前がある前提で領域を取る

### F. データコールアウト
```
        85 : 1
   サイレント修正 ： 公開アドバイザリ
```
- 中心の数字を目立たせる。比較・母数・期間に必要な値は残し、独立した主張が複数なら分割や別の型を選ぶ。
- 数字を大きくしても、単位や対象のラベルを読めない大きさにしない。会場に合わせて調整する。
- **比の向きと母数を必ず本文に書く。**「85:1」だけでは伝わらない

### G. 階段（包含関係）
```
18,475      読んだ修正の総数
   2,225    そのうちセキュリティ修正
      1,808 そのうち根拠が強いもの
```
- 字下げが**部分集合**を意味する。並列を字下げで書かない
- 母数の違う数を同じ階段に混ぜない
- 3 段まで

### H. 対比 2 カラム
```
肩書きで信じる    →    検証して信じる
肩書き                 証明
所属                   成果
```
- 左を弱い色、右を accent。矢印は 1 つ
- **項目は 3〜5。** それ以上は表にする
- 場所を食う割に情報量が少ない。1 行に畳めるなら畳む

### I. タイムライン
```
●───────────────────●
報告            半年            実害
```
- 両端に印、あいだに期間。**要素は 3 つまで**
- 縦に積むと年表になり、横に引くと因果に見える。目的で選ぶ

### J. 表
```
#35  ネットワーク層の耐量子化   量子計算機が来ても入り口が破られない
```
- **最終手段。** 全件を落とさず見せる必要があるときだけ
- 列見出しを必ず置く（空間的近接：ラベルを対象の隣に）
- 行は 8 まで。超えたら枚を割る
- **読み上げない。**目で追ってもらう枚だと口頭で宣言する

### K. 3 区画（行動を求める）
```
─────────   ─────────   ─────────
交通費        宿泊         条件
1 行          1 行         1 行
```
- **箇条書きにしない。**罫線で区切った区画にする
- 入れ子を作らない（「出すもの 2 件」の下に「条件 2 件」は 2 メッセージ）
- 連絡先は 1 つだけ、いちばん下に

## 4.5 図解の型（版面が決まったあと、中に何を描くか）

A〜K は**版面**の型で、「右半分に何を描くか」は決めていない。
そこは既存の分類を借りる。思いつきで描かないための対応表。

**集めた型の全在庫は `slide-type-catalogue.md`（69 型・出典つき）。**
ここに置くのは、そこから畳んだ最小限。迷ったらカタログの §7「畳んだ実用リスト」から選ぶ。

### Duarte の 5 系統（Slide:ology 第 3 章／Diagrammer）

Nancy Duarte が自社デザイナーのスケッチ数千点を分類して得た 5 系統。
**情報どうしの関係は、この 5 つのどれかに落ちる**という主張。

| 系統 | 表しているもの | この判型での描き方 |
|---|---|---|
| **Flow** | 順序・因果・循環 | 横 3〜4 箱 ＋ 矢印。循環なら下に戻り矢印 |
| **Network** | つながり・相互作用 | 節点と線。**5 節点まで**、超えると毛玉になる |
| **Stack** | 層・階層 | 横長バーを縦に積む。**どの層の話かを 1 層だけ着色** |
| **Segment** | 全体と内訳・分割 | 100% 横バー。円グラフより比較しやすい |
| **Join** | 合流・重なり・変換 | 2 つが 1 つになる矢印、または重なる領域 |

### Roam の 6W（The Back of the Napkin）

「その枚が答えている問い」から図の種類を機械的に決める。Zelazny のチャート版と同じ発想を、図全般へ広げたもの。

| 問い | 図 |
|---|---|
| 誰が・何が | 肖像・対象そのもの（写真／スクショ） |
| どれだけ | チャート |
| どこで | 地図・配置図 |
| いつ | タイムライン |
| どうやって | フローチャート |
| なぜ | 多変数プロット（2 軸・マトリクス） |

**使い方**：まず Roam で「この枚は何の問いに答えるか」を決め、
次に Duarte でその関係を描く系統を選ぶ。両方が同じ図を指せば、それが正解。

### 構成図（主体と行為）── 関係そのものを説明する場合

Duarte の Flow を、**AWS の構成図と同じ書き方**まで具体化したもの。
「全体の流れの中で、どの主体を通って何が起きるか」を 1 枚で見せたいときの既定形。
Stack・Segment・チャートで描きかけた図も、たいていこれに読み替えたほうが伝わる。

```
        ┌─ ここから先は機械が保証する ──────────────────┐
┌────────┐  命題を書く ┌────────┐ Lean に写す ┌────────┐         │
│ 研究者 │ ─────────→ │翻訳 LLM│ ══════════→ │証明 AI │  ...    │
│  人    │            │ モデル │             │探索と検査│       │
└────────┘            └────────┘             └────────┘         │
        └───────────────────────────────────────────────┘
写し取りを間違えると、機械は間違った命題に「証明済み」の印を押す。
```

| 要素 | 何を置くか | 決まりごと |
|---|---|---|
| **ノード** | 主体（人・モデル・検証器・市場・層） | 中に**アイコン**、名前（13pt）、種別を mono 10pt。**名前は 8 字以内**、超えると 2 行に割れて種別とぶつかる |
| **edge** | その主体が次に対して**すること**。動詞で書く | **ラベルは 8 字以内**で 1 行に収める。9 字を超えると隣の箱にはみ出す |
| **枠** | 保証・所有・信頼の境界（「ここから先は機械が保証する」） | ラベルは枠の左上外側。枠の底と脚注が重ならないよう下に余白を取る |
| **強調** | 赤茶＝まだ手が入っていない／壊れる場所、青＝検証が効いている場所 | **1 枚 1 箇所。** 全部に色を点けたら無強調と同じ |
| **戻り** | 循環しているとき | 下に 1 本だけ。矢印は先頭ノードの底に返す |
| **注記** | 図を読めない場合、または省くと範囲が変わる場合だけ | 対象の隣に 12pt・1 行。背景・読み上げ・既出事実はノートへ |

**アイコンと箱の形は必須。** AWS の構成図が読めるのは、箱の中の絵で
「これは計算資源／これは保管庫」が一目で分かるからで、
箱が全部同じ長方形だと、どれが人でどれが機械でどれが成果物か読めず、
図は結局「文字の羅列」になる。実際に外部レビューで全枚に対して指摘された。

- **アイコン**は 1 セットを自前で描く（人・モデル・検証器・鍵・台帳・投票箱・
  契約書・市場・チップ・工場・穴・錠前）。外部のロゴを混ぜると線幅と配色が合わない
- **描いたアイコンは、外の目に「何に見えるか」を言わせる。**
  作者には意図が見えているので自分では検出できない。実際に外部レビューで、
  意図した「工場」が**フォルダ**に、「AI モデル」が**チャット画面**に、
  「指数」が**空の箱 3 つ**に、「Ethereum の菱形」が**ただのひし形**に見えていた。
  聞き方は「これは何のアイコンだと思うか、意図を推測せず見えたまま書いて」
- **箱の形**で役割を分ける。**主体（人・AI）は角丸、機械・データ・場は角。**
  2 種類で足りる。細かい違いはアイコンが担う
- 色は 1 枚 1 箇所。赤茶＝まだ手が入っていない入口、青＝検証が効いている出口。**位置づけを固定する**
- 枠のラベルは**全枚で同じ文型**にする（「◯◯の範囲」）。
  保証の境界と秘密保持の境界が混在すると、枠が何を意味するのか分からなくなる

**作成計画の要点は、図の中にも現れていなければならない。**
図が示していない結論を、見出しや注記の一文で補わない。図からは「人が確認して製造する」
現状しか読めないなら、青い検証ノードを足すか、要点を言い過ぎない。

- ノードは **4 つまで**。5 つ以上は幅が足りず、ラベルが全部 2 行になる
- **矢印は 1 種類**。順序・因果・変換を形で描き分けない（色でだけ分ける）
- 同じ語をノードの種別と edge の両方に置かない（「検証者ノード／提案する」→「提案する」は重複）
- 7 枚並べるなら **7 枚とも同じ語彙**にする。1 枚だけ棒グラフにすると、そこで読み方の学習がリセットされる

### 選ぶときの注意

- **円グラフを使わない。** Segment は 100% 横バーにする（長さのほうが角度より正確に読める）
- **Network を安易に選ばない。** 節点が 6 を超えたら Stack か Segment に読み替えられないか疑う
- **矢印は 1 種類。** 順序・因果・変換を同じ矢印で混ぜない
- 図に添えるラベルは **12pt 以上**。図の中の文字は本文より小さくしていい理由がない

## 4.6 定番の枚（コンサル系デッキ）

ビジネス文脈で繰り返し出てくる枚。型が決まっているので、毎回設計し直さない。

| 枚 | 中身 | 決まりごと |
|---|---|---|
| **エグゼクティブサマリー** | 全体の主張を 1 枚 | SCR（状況→複雑化→解決）。解決に 60〜70% を割く |
| **ワンページャー** | 複雑な話を 1 枚 | 見出し ＋ 要点 3〜5 ＋ 次の行動 |
| **進捗** | 状態の共有 | 信号（赤／黄／青）・実績・次の節目・危険・決めてほしいこと |
| **規模** | 機会の大きさ | TAM/SAM/SOM。**前提と出典を必ず書く** |
| **チャート** | 主張の証拠 | 見出しは**データの解釈**であって「売上推移」ではない |
| **イシューツリー** | 問題の分解 | MECE。枝の粒度を揃える |
| **背景（現状の課題）** | なぜこれが要るか | 見出しだけで「これは課題の枚」と読めること。**実際に起きた事例を出典つきで置く**（§4.7） |
| **新規性（既存との差分）** | 何が新しいのか | 既存の機構と、その上に重ねたものを**左右に分けて**置く。比較表だけでは答えにならない（§4.7） |

## 4.7 技術説明で確認する背景と差分

### (a) その枚の役割と内容が分かるか

背景・結果・新規性・限定のどの役割なのか、見出しと主視覚から分かるようにする。
必要なら「背景：〇〇で△△が起きる」のように役割と具体的な内容を併記する。
既に文脈が明白な節扉等では名称だけでもよい。役割名を追加すること自体を目的にしない。

### (b) 課題は実際の事例で示せるか

抽象的な問題を長く説明するより、適切な実例を選ぶ。件数は固定せず、1件を具体的に追う構成でもよい。

- 一次資料で事例と主張の範囲を確認する。
- URLの表示位置は利用者・テンプレートの指定に従う。本文に置く場合も可読性を確認する。
- 分野の異なる例を比較するなら、共通する条件と違う条件を明らかにする。
- 詳細な出典を巻末へ移しても、発行元・対象・重要な限定を失わせない。

### (c) 比較から具体的な差分が分かるか

比較表だけで新規性が伝わらない場合は、既存機構と追加・変更した箇所を明示する。
同じ枚で強調できるか、具体的な差分の画像・実行結果が適切かを先に判断し、必要な場合に別ページへ分ける。
既存の部分を自分の成果に帰属させない。専門的な権利判断が依頼の目的でなければ、特許性等の論点を追加しない。

## 5. やってはいけない

| ✗ | なぜ |
|---|---|
| 意味のない枠を増やす | 区切りは余白や罫線で足りる場合が多い。比較やUIの再現に必要な枠は残す |
| 文字数で級数を変える | 揃っていないだけに見える |
| 重要な人物・値・文を切って揃える | 外側の切り取りは可能だが文脈を保つ。縦横比を変形させず、必要ならcontainで収める |
| 凡例・脚注に飛ばす | 空間的近接の違反。ラベルは対象の隣 |
| **図の符号の意味を画面に書かない** | 塗り分け・形・線の太さに意味を持たせたのに、その対応を発表者ノートにしか書いていない。**画面だけ見る人には無地の丸が並んでいる**（§5.1） |
| 全部を強調する | シグナリングの違反。1 枚 1 箇所 |
| スライドの文をそのまま読み上げる | 冗長性の違反。読む処理と聴く処理が競合する |
| 詰めて 1 枚に収める | 分割の原則。枚を割るほうが伝わる |
| 内容と無関係に分割比率を決める | 比較なら対称、画像と要点なら非対称など、情報の役割で選ぶ |
| 縦位置を目分量で置く | 行グリッドから外れる。§2.5。**「崩れて見える」の第一容疑者** |
| 1 枚の中で基準点を top と FOOT_Y で混ぜる | ブロック間の間隔が枚ごとに変わる |
| 図の中の語を 2 か所に書く | ノードの種別と edge が同じ語だと、読む側は違いを探して止まる |
| 4 つ以上を「3 カラム」で並べる | 一覧に見える。E のグリッドへ |

### 5.1 符号を使ったら、図の中で言い切る ★★

塗りつぶし／白抜き、実線／破線、線の太さに意味を持たせたら、**その意味を画面に置く。**

実測：時間軸 2 本に丸を並べ、**塗りつぶし＝その時点で照合する**という符号を使った枚で、
対応を発表者ノートにだけ書いていた。依頼者の指摘は
**「図が非常にわかりづらい。それぞれなにをするものなのかそもそもわからない」**。
符号が読めないので、図は「丸が並んでいるだけ」に見えていた。

直し方は 3 つ重ねる。1 つでは足りない。

| 置くもの | 位置 | 役割 |
|---|---|---|
| **凡例 1 行** | 図の上 | ●＝この時点で照合する　○＝この時点では照合しない |
| **各記号の直下の語** | 対象の隣 | 丸ごとに「照合する」「照合しない」。凡例まで目を往復させない |
| **結果の欄** | 図の右端 | その符号の違いが何を生むか。符号だけでは「だから何」が出ない |

**比較の図では、同じ入力を上下に同じ形で描く。** 上下で違うのは符号だけ、という状態に
すると、「入力が同じで結果が違う」が図そのものから読める。片方にだけ事象を描くと、
読み手は「下の構成ではこれが起きないのか」と誤読する。

## 6. 監査のしかた

各枚について以下を確認する。型を付けただけで分かりやすさを判定しない。

1. **主視覚と版面は何か**（例：`C + 実記事スクショ`。図を描く場合は関係の種類も選ぶ）
2. **見出しから具体的な主張・対象が分かるか**。主視覚がそれを支えるか
3. **主視覚が要点を示しているか**。文字の列で図の役割を代替していないか
4. **全ブロックが同じ行の単位に乗っているか**（§2.5。座標を並べて倍数か目で見る）
5. **その枚の役割（背景／仕組み／比較／新規性／限定）が、見出しだけで読めるか**（§4.7a）
6. **図に符号を使っているなら、その意味が画面に書いてあるか**（§5.1）

同じ型の枚が並ぶときは、`measure.py` の**図形数・段落数・文字数が揃っているか**を見る。
揃っていれば型どおりに組めている。1 枚だけ数字が飛んでいたら、そこが型から外れている。

実測を添える：

```bash
# 図の数・段落数・文字数を枚ごとに出す
uv run assets/measure.py out/deck.pptx
```

図が 0 で 250 字を超える枚が続いていたら、そこが谷になっている。
