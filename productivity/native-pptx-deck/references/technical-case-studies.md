# 技術事例を一目で理解できるスライドにする

学会の招待講演や研究ツールの紹介で、実装の具体性と説明の簡潔さを両立させるための判断基準。
スライド枚数やレイアウトの固定テンプレートではない。

## 1. 骨子の前に、見せられる事例を作る

全体の物語を決める前に、どんな構成でも使う事例紹介を作り込む。
「Lean / SMTでこんなこともできるのか」という驚きは、実際の対象と成果から生む。
ツール名・抽象的なパイプライン・効能だけでは、初見の聞き手は追えない。

リポジトリのREADMEに加え、実装、仕様・assertion、検証コマンド、結果・反例を読む。
内部メモには参照コミット・ファイル・実行条件を残し、次を具体語で答えられるようにする。

- **道具と対象:** 何を入力し、何を調べ、何を出すツールか。
- **動作原理:** どの表現に変換し、何を探索・検査・証明するか。
- **発見:** どの箇所が、何を期待したときに、どう違ったか。

この3問を必ず3枚に分ける必要はない。1枚で伝わるものは1枚にする。
論文引用は必要箇所に `Chen et al. ’22` のように短く置き、完全な書誌・URLはノートへ。
論文の方式、公開実装の不具合、自分たちの改良を区別し、著者・年・対象版は根拠で確認する。

## 2. 図の種類は、伝える関係で選ぶ

「分かりにくい」への修正は、まず対象の具体化、視線の整理、不要要素の削除から始める。
説明文や箱を足して埋めない。図の種類を変えること自体も目的にしない。

| 聞き手に見せたいもの | 主視覚と読み順 |
|---|---|
| 計算と実装の対応 | 数式から同じ変数名の回路へ。入力、演算、出力を追える配置 |
| 回路の誤り | 大きな回路図で欠落箇所を強調し、隣に期待式と実際の出力 |
| 改良の差分 | 同じ向き・記号の回路で変更部を強調し、その部品に削減量を直結 |
| 状態の許可・拒否 | 具体的な状態・遷移と、残す領域・除く領域を示すグラフ |
| 値の抽象化 | 条件の真偽が同じ入力をまとめた区間表 |
| ツール間の役割 | 入出力と処理主体を示すアーキテクチャ図 |
| 依存関係 | 実データのグラフ。必要なノード・辺を絞って関係を強調 |
| 実行結果 | 入力と観測値が読める実画面、短いデモ、または大きな結果値 |

1枚の主視覚を1つ決め、入り口→操作・変化→結果を一方向に追えるようにする。
2つの独立した図を上下左右に並べると、関係の解読を客席へ押し付ける。
比較が必要なら、対応する部品を揃えた一体の比較図にする。
連続ページも見て、同じフロー図やノードグラフの反復で説明が進まなくなっていないか確認する。

回路の配線は直線と直角折れを基本にし、分岐・接続点・非接続の交差を区別する。
状態グラフの戻り辺には曲線が有効な場合もある。回路を装飾的な曲線ネットワークにしない。
Lean等のロゴは処理主体を識別する位置に使い、どの処理がLeanなのかをラベルで明確にする。

## 3. 形式検証は「何を、どう、どこまで確かめたか」を描く

例えば「INTT往復の検証結果」だけでは、検証内容も発見箇所も伝わらない。
根拠がある場合、次の情報を回路と直接結び付ける。

- 検査対象の実装とツール・方式（例: Yosysによる有界な出力式の検査）。
- 入力範囲・モード・初期状態・クロック数など、主張を変える条件。
- 比較した期待式と実出力。両出力で `/2` が欠落したなら、両方の位置を強調。

`0 ≤ u,v,w < q` の全入力、6クロック後の出力という限定は、確認した範囲として示す。
固定深さの検査を任意時刻の正しさへ、単一モジュールの結果を回路全体へ拡張しない。
演算器の数、演算回数、FPGAのLUT資源数、定数Lookup Tableの語数も区別する。

Leanの適用では、分野の概念と実装上の対象の対応を見せる。
例えば監視制御なら、実コードの更新前後を状態に、書込みを遷移に対応させ、
どの遷移を止められ、どの状態を除くのかを1つの実例で示す。
解析器の仕事、Leanが検査する性質、実行時に観測したことを混同しない。

学術性は注釈の量で補わない。結論の解釈を変える前提は画面に残し、
既に共有したsolc/Yul等への信頼前提を毎回「証明書の限界」の独立スライドにしない。
形式仕様や検証の根拠を示せない監査事例は、形式検証の成果としてまとめない。
SPECA等の名称だけで判定せず、その発表で扱う実施内容で選別する。

## 4. 改良は回路の差分と削減箇所を見せる

AIによる候補作成→モデル検査→修正を説明する場合、中心には得られた回路を置く。
不合格候補を除きながら改善したことを短く添え、工程図だけで1枚を埋めない。
AIが発見したと述べるときは探索履歴等を確認し、人間の改良をAIへ帰属させない。

共通部は同じ位置・色に保ち、変更部だけを強調する。細かい修正の列挙はノートへ。
「乗算器 3基→1基」は該当する演算器のそばに、
「定数テーブル 1023語→512語」は残す領域と除いた領域のそばに置く、というように
**数値を図中の削減箇所に結び付ける**。数値は事例の根拠に従い、「半分」と丸める範囲も明示する。
公開成果にはFoldNTT等のリポジトリへのリンクを付ける。

## 5. 足す前に引く

- 前ページで対象・方法・結果が伝わるなら、その言い直しだけのページを削る。
- 小さい章タイトル、同内容のリード・締め、当然の微修正の列挙を省く。
- デモは実際の入力・操作・結果を大きく見せる。模擬映像は検証結果の証拠と扱わない。
- 動画はリンクの存在だけで判断せず、配布先で表示・再生できる状態にする。
- 図だけを見て「対象」「変化した箇所」「結果」を指せるかを見る。
  分からなければ、要素を追加する前に変数名・対応関係・強調位置を直す。

手動で簡潔に直された版は、その情報量と省略の判断もフィードバックとして扱う。
削った説明を次の生成で自動的に復活させない。
