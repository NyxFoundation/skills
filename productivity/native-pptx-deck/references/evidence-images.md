# 実物を、証拠として見せる

読む場面：記事・投稿・法令・論文・製品・ツール画面の採用、難解な図の置換。

## 1. 何を示す画像かを先に決める

| 役割 | 必要な画像 | 不十分な代替 |
|---|---|---|
| 誰が発表したか | 発行元・著者・日付と、発表内容が分かる範囲 | 見出しだけの文字片、ロゴだけ |
| 実在する製品・仕組み | 実機写真・公式画面・外部の原図 | それらしく生成したUIや抽象的な箱 |
| 設定すると何が制限されるか | 設定名、値、単位、対象権限が分かる実画面 | 製品のトップ写真だけ |
| 何が起きたか | 入力、観測結果、実行条件 | ソースだけ、成功したように組版したログ |
| 数値の根拠 | 結果の載る表・グラフ・該当本文 | 論文の表紙や記事のタイトルだけ |

元資料の画像・図がそのまま明快なら使う。自作する場合も、関係が分かることを目的とし、箱・矢印・アイコンの数を成果にしない。

## 2. スクショの範囲

- **ブログ・発表**：会社や媒体の識別、題、著者・日付、要点が分かる概要・導入を含める。必要に応じて人物・公式図・写真まで残す。
- **SNS投稿**：投稿者・ハンドル・日付と、主張に関係する投稿本文全体を写す。限定や否定を切り落とさない。スレッドなら親投稿との関係を記録する。
- **法令**：公式サイト・法令名・条番号を識別できる文脈と該当条文。データ最小化と保存制限のような別原則を一緒の条項にしない。
- **論文**：題・著者・版を示す文脈と、採用する結果の箇所。表の一行だけで意味が決まらなければ列名・条件も残す。
- **製品UI**：製品が識別でき、対象の設定値や出力が見える範囲。無関係なサイドバーで要点を縮めない。

切り取りは「最小の文字片」ではなく、**出所と意味が決まる最小の文脈**にする。
画像の下端に次の行の文字片を残さず、本文や数値を途中で切らない。

## 3. 文脈と可読性を両立する

Webページ全体を縮小しただけでも解読は必要になる。

- 出所と実物を示す画像に、大きい日本語の要点を短く添える。原文全文の精読を求めない。
- 設定値や結果を実際に読ませる場合は、その箇所を拡大する。
- 両立しない場合は、文脈を見せる画像と該当箇所の拡大を組み合わせるか、2枚に分ける。
- タイトル画像だけでは本文の主張を支えない場合、概要・本文・結果まで写す。画像を足すだけで済ませない。
- 外国語の短い要約は要約と分かる形にし、元の発言を超えない。

例えば、ロゴと記事名で発行元を示しても「投資を発表した」ことしか読めないなら、「全製品が形式証明された」という見出しにはできない。

## 4. 撮影と来歴

利用可能な接続ツール・ブラウザ等で原ページへアクセスし、実際の画面を取得する。
原画像を保存し、出典URL、取得時点、著者・公開日・版、切り取り範囲、必要なら参照コミットを記録する。保存形式は既存プロジェクトに合わせる。

Webのズーム、レスポンシブ表示、Cookie通知を閉じる操作、外側の切り取りは、意味を変えずに行い、再現に必要な条件を記録する。
発言・数値・日付・著者を書き換えた画像を、原画面として扱わない。別資料のロゴを合成して発言元を捏造しない。装飾用の生成画像を実在の機器や実績の証拠にしない。

取得できない資料は、ユーザー提供の原本や別の適切な一次資料を使う。欠けた発表や結果を架空のスクショで埋めない。

## 5. コード・実行画面

説明用コードと本番の実例は区別し、説明用なら画面にも短く明示する。

1. 同じ保存済みソースを実行し、入力・出力・コマンド・バージョンを記録する。
2. IDE等へ貼り付けた場合は、エディタの実際のソースが保存済みファイルと一致するか確かめる。Monaco等の自動インデントに注意する。
3. エラー・警告・検査待ちを解決し、実際の診断を表示して撮影する。成功表示を描き足さない。
4. 修正前の失敗と、修正後の証明を混同しない。任意入力、前提条件、検査した性質の範囲を残す。

「コードが通った」という小さい表示だけに意味を背負わせず、「残高を超える出金を拒否した」等の具体的な入出力や性質を要点にする。

## 6. 採用前の判定

- その画像は誰の何か分かるか。
- 主張の根拠となる箇所が実際にあるか。
- 日本語の要点だけで意味を追え、必要な値は読めるか。
- 引用範囲、文脈、版、著者の限定を保っているか。
- 自分の提案・説明例と、第三者の実施実績が区別できるか。

この条件を満たさないときは、画像を大きくするだけでなく、資料選択・主張・ページ分割を見直す。
