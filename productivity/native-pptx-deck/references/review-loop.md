# Recursive external review

書いた草案は成果物ではない。**独立したエージェントに殺されにきてもらって、生き残ったもの**が成果物。
4〜7 周を見込む。**`assets/selfcheck.py` を先に通せば 2〜3 周で済む。**

スライド固有の事情が 2 つある。

1. **レンダリングして見ないと分からない欠陥がある。** python-pptx はテキストの溢れにも、
   存在しないフォントにも、無言で失敗するプロパティにも例外を出さない。
   毎周 PNG を書き出して**自分の目で見る**。これはレビュアーに任せられない
2. **構成の欠陥は文章で先に潰す。** 絶対座標で 12 枚組んでから構成をやり直すのは高い。
   スライド一覧の表を先に合意する

---

## 周回を減らす — 先に機械で潰す

```bash
uv run assets/selfcheck.py out/deck.pptx      # exit 0 になるまで外部レビューに出さない
```

実測：あるデッキのレビュー R1・R2 で出た **19 件のうち 14 件（74%）が機械的に検出できた**。

| レビュアーの指摘 | 対応する検出 |
|---|---|
| S05 と S06 が同一キッカー | キッカー重複 |
| 順路①が対外セクションを覆っていない | 目次の網羅（参考） |
| 「N つ」と実際の項目数が合わない | 数詞と実体数 |
| Eris が一覧に載ったきり出てこない | 孤立した実体（参考） |
| SPECA / Atlas Prover が二度と出ない | 孤立した実体（参考） |
| 43 件に対し内訳が 7 + 21 で合わない | スライド間の算術 |
| 15 < 21 なのに「いちばん多い」 | スライド間の算術 |
| 見出しが「呼ばれました」で活動記述 | 見出しパターン |
| 見出しが「問われています」で曖昧 | 見出しパターン |
| 見出しが体言止め | 見出しパターン |
| 1.2% の母数が書かれていない | 数字のラベル |
| 1 枚に等列 4 項目で負荷が高い | 項目数（参考） |

**残る 5 件は判断が要るもの**で、機械では出ない：

- 場の趣旨（「何に困っているかを話す場」）に対して内容が足りていない
- 1 枚に対象も行動も違う 2 つのメッセージが同居している
- 実成果と非開示が同列に並んでいて、両方の伝わり方が弱い
- 事実の重さが、この聞き手には測れない
- タグラインが願望であって研究記述になっていない

**これがレビュアーに探させるべきもの。** ゲートを通さずに出すと、
レビュアーは 1 周目の予算を正規表現で見つかるものに使い切る。

### ゲートが意図した設計で鳴ったら、ゲートのほうを直す

実測 1：全 43 件を意図的に列挙するデッキで「項目数」が 7 枚に発火した。設計どおりなのに NG が出る。
実測 2：全スライドにページ番号を入れた直後、「数字のラベル」が発火した。額縁の要素は
単独で置かれるのが正しい。**体裁そのものに発火するゲートは即座に信用を失う。**
**この状態を放置すると、ゲートの出力を読み飛ばすようになり、本当の検出も一緒に見逃す。**
判断が要る検査は「検出」ではなく「参考」に降ろす。検出に残すのは、
**設計意図に関係なく間違いと言い切れるもの**だけ。

### 機械化を試して捨てた検査 ── 枚をまたいだ言い直し

`slide-copy-rules.md` §6.2(c)「前の枚で言ったことを締めで繰り返す」を
文字 3-gram の重なりで検出しようとした。**実装して 12 件全部が誤検出だったので捨てた。**
再実装しないよう理由を残す。

- **共有された固有名詞で誤発火する。**「AI エージェント」を含む別々の文が
  互いに似ていると判定される。帯名を一覧の枚と各論の枚で再掲するのは**設計上の意図**なのに、
  そこが最も強く鳴った
- **本当に取りたい重複は語彙が一致しない。** 実例の
  「Nyx Office Hour は毎月開きます。」と「毎月 3 名を、交通費と宿泊つきで招待します。」は
  共通する 3-gram がほとんど無く、閾値をどこに置いても検出できない

つまり**語彙の重なりでは、ノイズだけ拾って本体を逃す**。
これは意味の重複なので、Pre-flight checklist（人の目）と外部レビューの設問に回す。
「機械で潰せる指摘は先に潰す」の原則は、**機械で潰せない指摘まで機械に押し込む理由にはならない**。

## Mechanics

### 毎周のレンダリング

```bash
bash assets/render.sh out/deck.pptx /tmp/render
```

`p-00.png` … と `contact.png`（コンタクトシート）が出る。

**必ずコンタクトシートを先に見る。** 溢れ・衝突・空白の偏りは縮小画像のほうが見つかる。
そのあと個別の枚を開いて文言を読む。

LibreOffice は nix で引ける（`nix-shell -p libreoffice-fresh`）。
**ただし PowerPoint の描画とは一致しない。** 特に折り返し位置が違い、それが溢れの有無を決める。
「LibreOffice で問題なかった」は「PowerPoint で問題ない」を意味しない。

### レビュアーに渡すもの

`.pptx` は読めない。**テキストを抜いて渡す。**

```python
# extract_pptx_text.py
import re, sys, zipfile
from xml.etree import ElementTree as ET
A = "{http://schemas.openxmlformats.org/drawingml/2006/main}"
z = zipfile.ZipFile(sys.argv[1])
for n in sorted((n for n in z.namelist()
                 if re.match(r"ppt/slides/slide\d+\.xml$", n)),
                key=lambda s: int(re.search(r"\d+", s.split("/")[-1]).group())):
    root = ET.fromstring(z.read(n))
    print(f"\n--- {n.split('/')[-1]} ---")
    for p in root.iter(A + "p"):
        t = "".join(r.text or "" for r in p.iter(A + "t"))
        if t.strip():
            print(t)
    # スピーカーノートも渡す（意図が書いてある）
```

構成レビューなら**スライド一覧の表**だけでよい。文言レビューなら全文。

### 呼び出し

```bash
timeout 900 hermes -z "$(cat review-prompt.md)" -m glm 2>&1 | tee review-r1.md
```

- プロンプトはファイルに書く。`$( )` の中のヒアドキュメントは壊れる
- 出力は長いので必ず `tee` で残す。次の周で参照する
- 別モデルを使う。自分で書いたものを自分でレビューしても構造的欠陥は出ない
- 代替：`codex exec --skip-git-repo-check ... < /dev/null`（`< /dev/null` は必須）、
  読み取り専用ツールセットの Claude サブエージェント

## Prompt design

### Round 1 — 全部出させる

```
以下は <場の名前・性格> で <所要時間> 話すスライドデッキの全文です。

聞き手: <誰か。何を知りたくて来ているか>
会の性格: <「雑に話す場」なのか、審査なのか。ここを外すと的外れなレビューになる>

使っている規則:
- 見出しは Assertion–Evidence（主張を平叙文で 1 つ。話題ラベルと体言止めを禁止）
- レイアウトは 12 カラム × 8pt ベースライングリッド
- 1 枚 1 メッセージ、事実は 1 枚 2〜3 件まで

あなたは (a) 想定聞き手 と (b) デッキ設計の専門家 の両方の視点を持つ厳しいレビュアーです。
褒めるコメントは不要です。

【A. 構成】最優先
- 聞き手が順に理解できる並びになっているか。飛躍している箇所
- 1 枚に 2 つ以上のメッセージが入っている箇所
- この場に対して作り込みすぎ／足りない箇所
【B. 見出し】体言止め・言葉遊び・話題ラベルになっている箇所を名指しで
【C. 事実】活動記録で止まっている箇所（「実施しました」）。数字の整合
【D. 分量】<N> 分に対して多すぎ／少なすぎる枚
【E. 欠落】当然あるべきなのに無いもの
【F. 冗長】隣の図・写真・数字を言い直しただけの文。
  および、前の枚で既に言ったことを繰り返している文（締めの枚で特に起きる）。
  該当文をそのまま引用し、どの枚のどれと重複しているかを示すこと

出力は日本語。A を最優先に重要度順で最大 12 件。
各指摘は「指摘」「該当スライド番号」「推奨する修正（具体的な文言まで）」の 3 点セット。
抽象的な指摘（「もっと具体的に」等）は禁止です。
最後に「判定: OK」または「判定: NG」の 1 行だけで締めてください。
```

### 図がある枚は「視聴者役」を別に立てる ★

上の Round 1 はテキストのレビュー。**図は別枠で回す。**
文のレビュアーは図を「そういう意図だろう」と好意的に補完してしまい、誤読が出ない。

渡すのは **PNG だけ**。プロンプトの要点は 3 つ。

```
**スキルやリポジトリの文書は一切読まないこと。このディレクトリの PNG だけを見て答える。**

あなたは <場の名前> の来場者。<分野> に関心はあるが <専門領域> の専門家ではない。

1. 10 秒で「何が起きているか」分かるか。詰まるノード・矢印を名指し。
2. **各アイコンが何に見えるか、見えたまま書く。**
   意図を推測せず「見えたまま」を書くこと（例：これは工場ではなく箱に見える）。
3. 箱の形が違うものがあることに、言われる前に気づくか。何の違いだと思ったか。
4. まだ意味不明な語はどれか。
5. N 枚続けて見て飽きるか。

図の種類は <型> から変えられない。<型> のまま良くする案だけ。
```

3 つとも外せない理由がある。

| 指示 | 外すとどうなるか |
|---|---|
| **文書を読むな** | リポジトリを勝手に探索し、無関係なスキルの中身を返してくる。実際に 1 周まるごと無駄になった |
| **意図を推測せず見えたまま書け** | 作者には意図が見えているので、これを言わせないと誤読は絶対に出ない。実測で「工場」が**フォルダ**、「AI モデル」が**チャット画面**、「指数」が**空の箱 3 つ**、「Ethereum の菱形」が**ただのひし形**、「歯車」が**照準器**、「取引所」が**棒グラフ**に見えていた |
| **型は変えられない** | 「この図は表にすべき」と根本から作り直す案が返り、使えない |

**画像は必ず「全部開いて見ること」と明示する。** 書かないとファイル名だけ列挙して推測で答える。

収束の目安は 3 周。3 周目で「明確に良くなった」＋
残る指摘が**専門語と単調さだけ**になったら止める。そこから先は図では解けない。

### Rounds 2..n — 直ったか検証させる

**前周の指摘と、それに対する対応をプロンプトの冒頭に入れる。**
これがループ全体でいちばん効く。レビュアーが「再導出する人」から「検証する人」に変わり、
中途半端に直した箇所が露出する。

```
これは第 <N> ラウンドです。

前回あなたは「判定: NG」を出し、致命的欠陥として <要約> を挙げました。

反映内容:
- <指摘> → <どう直したか>
- ...

以下は改訂版の全文です。

検証してください:
【A】上記が本当に解消されているか。不十分なものを具体的に
【B】修正によって新たに生まれた問題（特に <今回変えた箇所> と他の枚の整合）
【C】まだ残る致命的欠陥

実害のある問題のみ、最大 <前回-2> 件。
最後に「判定: OK」または「判定: NG」の 1 行だけで締めてください（重複して書かないこと）。
```

上限を毎周縮める（12 → 8 → 6 → 5 → 4 → 3）。優先順位付けを強制し、収束の合図にもなる。

### 最終ラウンド — 判定だけ

```
これは最終確認です。出せるかどうかだけを判断してください。
止めるべき実害のある問題が残っていれば最大 3 件挙げ、なければ「なし」と明記してください。
細かい精緻化の提案、文体の好み、さらに厳密にできる余地の指摘は不要です。

注意: あなたは <N> ラウンド連続で NG を出しています。改善が十分なら OK を出してください。
ただし妥協して OK を出す必要はありません。致命的欠陥（デッキの根幹が機能しない欠陥）が
残っている場合のみ NG とし、細部の改善余地は OK としたうえで指摘してください。

「判定: OK」または「判定: NG」の 1 行だけで締めてください。
```

最後の段落が無いとループが終わらない。有能なレビュアーは必ずもう 1 つ改善案を出せる。

---

## 判定行を信じすぎない

**実測で起きたこと**：「判定: OK」と書きながら、本文では
「致命的な欠陥が 3 つ残っている」と書いてくることがある。逆に、
妥協禁止の但し書きを入れないと NG が延々続く。

**判定行だけで打ち切らない。本文の指摘を読んで妥当なものは反映する。**

## Triaging findings

**指摘は自動的に正しいわけではない。** 分類する。

| 種別 | 対応 |
|---|---|
| **正しい** | 推奨どおり直す |
| **診断は正しいが処方が違う** | 根本を自分のやり方で直す。乖離を記録する |
| **依頼者の明示的な指示と衝突する** | **従わない。**懸念だけ別の方法で満たし、指摘と却下理由の両方を報告する |
| **範囲外**（文体の好み、さらなる精緻化） | 却下。次周のプロンプトを締める |

第 3 種の実例。レビュアーは
「コラボの依頼で『全部に手を貸してほしいわけではありません』と否定文から入るのは、
信頼を作るので残すべき」とは言わず**逆に「門を狭めるシグナルになる」**と指摘した。
依頼者は「雑に話してコラボを作る場」と明示していたので、指摘を採用し
**「今日いちばん人を探しているのは、ここです」**という肯定形に置換した。
募集していない案件はスライドから外し、聞かれたら口頭で答える運用にした。

## 繰り返し出る指摘

先に潰しておく。レビュアーの確実な当たり所。
★ が付いているものは `assets/selfcheck.py` が検出する。

1. ★ **見出しが話題ラベル**（「〜の話。」「〜こと。」）または活動記述（「〜しました。」）
2. **1 枚に 2 メッセージ** — 目次的な図と、その枚の主張が同居している
3. **次の枚の中身を予告している** — 反転の効果が半減する
4. **抽象が連続する区間** — カード grid が 3 枚続くなど。ここが谷になる
5. ★ **一覧に載せたきり触れない固有名** — 聞き手の中で宙に浮く
6. ★ **スライドをまたいだ数の不整合** — 合計と内訳、最上位の主張
7. **事実の重さが聞き手に測れない** — 専門用語の言い換えを添えても「分かりやすくなる」だけで
   「重さが伝わる」わけではない。影響範囲か、まだ無いものか、何が変わったかを添える
8. **活動記録で止まっている**（「実施しました」）
9. **クロージングがリンクの列挙**になっている
10. **下 1/3 が空いている**枚が複数ある
11. **数字の先出し**で、後半の山を自分で潰している
12. **場に対して作り込みすぎ** — 勉強会に熱量設計を持ち込むなど

## Convergence

健全な推移（ゲートを通してから）：

```
R1  NG — 9 件   (ファクトの重さが聞き手に伝わらない / 命題と証拠のカテゴリ不一致 / …)
R2  NG — 6 件   (命題を弱めた副作用 / 予告の先回り / 目次スライド化)
R3  NG — 4 件   (2 行目が不在の指摘のまま / 中盤が横ばい)
R4  OK          (根幹は機能。残りは 1 行修正で済む 3 点)
R5  OK          (前提が変わったため再実施。着地の二股 / 数字が命題を食う)
```

件数が下がらなくなったら症状を直している。分類を読み直す。
たいてい**構造的な決定**（並び順、何を主張するか、どの層を落とすか）を変える必要がある。

前に通った箇所で**新しい指摘**が出続けるなら、修正が退行を生んでいる。
テキストを抜き直して周回間で diff を取る。

## 前提が変わったら周回をやり直す

実測で起きたこと：4 ラウンド回して OK を得た後、**発表する場の性格が判明した**
（「スライドや完成された発表ではなく、雑に話す場」と明記されていた）。
聞き手の想定が根本から違っていたので、構成を組み直して 5 周目を回した。

**Step 1（聞き手）と場の性格は、レビューより先に確定させる。**
そこが違うと 4 周分の作業が無駄になる。資料に書いていなければ依頼者に聞く。

## Reporting the loop

依頼者には正直に伝える。何周回したか、判定はどうだったか、どの指摘を却下したか。
**周回数は厳密さの証拠であって、初稿が弱かった証拠ではない。**

- 受け取っていない判定を主張しない
- 「判定: NG」を「軽微な修正で済む」と言い換えない
- ローカルで再現できない環境の問題（Google Slides のインポータなど）は、
  直したつもりでも**確証がないと明示する**
- `[要確認]` が残っているなら、どこに残っているかを言う
