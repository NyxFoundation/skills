# surface: terminal

A shell session with a run panel — for CLIs, build/test tools, coding agents, pipelines, anything whose value arrives as streaming output.

## What to fill in

| Part | What it must say |
|---|---|
| title bar | the real shell/tab name and `~/path/to/project — 148×36` |
| `#term` | 14–20 output lines by the end. A half-empty terminal reads as a mockup |
| `#tasks` | the plan the tool executes, 4–6 steps, in the tool's own words |
| `#sideMeta` | tool name + version |
| `#sum` card | the number the viewer should leave with (time saved, issues found, cost) |
| status line | session, branch, model/mode, tokens/duration — whatever your tool actually tracks |

## Markup rules

- Terminal lines are generated by `D.tline(html)`, never hand-written. Spans:
  `.p` prompt `.d` dim `.h` highlight `.w` warn `.e` error `.k` ok `.a` accent.
- Output arrives one line at a time, 300–500 ms apart, with dim `(1.8s)` timings.
  Nobody believes a tool that produces its result instantly.
- The important result goes in a `.box` (bordered card inside the terminal) — that is
  the one thing the viewer will read twice.
- Long-running steps get `D.barline()` + `D.fill()`, or a `.task.run` spinner in the panel.

## Surface helpers (on top of the core D.*)

| helper | use |
|---|---|
| `D.step(id, 'run'\|'ok'\|'bad'\|null, dur)` | run-plan row state + its timing |
| `D.barline(id, label)` / `D.fill(id, pct)` | progress bar inside a terminal line |
| `D.card(on)` | reveal the result card |
| `D.cls(D.stage,'split')` | slide the run panel in |
| `D.busy(on)` | pulse the session chip in the status line |

## Story shape that works

idle prompt → the command typed at ~38 cps → the plan appears (the tool tells you what it
will do) → work streams in with timings → the finding, boxed, that justifies the tool
→ fix applied, all steps green, result card.

If the tool is an agent, let it narrate a decision, not just a result — one line of
"why" beats three lines of "what".
