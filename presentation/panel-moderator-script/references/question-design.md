# 質問の設計

> **この文書の例は、実際のイベントの台本から取っています。**製品名・金額・年・人数は
> そのイベントのもので、**そのまま持ち込むと嘘になります。**書き換えの型として読み、
> 中身は一次情報で取り直してください。

**鋭さを先に作り、そのあと答えられるかを検査する。**順番を逆にすると、二度と鋭くならない。

---

## 5 つの規準

1. **固有名詞をこちらから先に出す。**調べてあることが伝わると、相手の出し方が変わる
2. **意見ではなく決断を聞く。**「どう考えますか」ではなく「何を選び、何を捨てたか」
3. **成功事例ではなく、止めた話から入る。**うまくいった話は広報が出している
4. **数字か固有の指標をひとつ要求する。**ひとつ出ると、そのあとが全部具体になる
5. **2 人の答えが割れるように作る。**割れたところが山場になる

---

## 3 つの禁止

**これは鋭さとは関係ない。**答えられない質問を投げても、返ってくるのは一般論で、
**鈍い質問と同じ結果になる。**

| 禁止 | 例 | なぜ |
|---|---|---|
| 個社を特定させる | 「お客様の何割が KPI に載せていますか」 | 顧客の内部指標を答えさせることになる |
| 未公表の社内方針を言わせる | 「御社ではいくらまで通りますか」 | 上場企業はリスク許容度と統制方針を出せない |
| 将来を断定させる | 「3 年後にはどうなりますか」 | 事業見通しの表明になる。外れたとき本人が困る |

加えて、**セキュリティ領域では攻撃経路そのものを聞かない。**
「いちばん安い侵入経路は」は、守秘にも安全にも触れるうえ、
**会場に残るのは防御策ではなく手口**になる。

---

## 鈍らせずに答えられるようにする書き換え

**問題があるからといって質問を薄めない。切り分ける。**

| 鈍い / 答えられない | 書き換え |
|---|---|
| 詰まっているのは技術ですか、承認ですか | **本番へ移すのを最後に止めたゲートを、ひとつ挙げてください**（社名も数字も伏せて構いません） |
| 権限・ログ・再現性のどれが厳しいですか | **未達なら本番に上げない、という条件をひとつ。何を見て判定しますか** |
| どの要件が足りなくなりますか | **本人を確認したあとに、それでも残る空白はどこですか。それを埋めるには何を記録しますか** |
| いちばん安い攻撃経路はどこですか | **ベンチマークは通っているのに、これがあるから実運用には出せない。その決定打は何ですか** |
| 御社では、いくらまでなら通りますか | **金額は伏せて構いません。何を測って、どの水準で合格と判定しますか** |
| 誤送金は取り消せますか。損失は誰が持ちますか | **技術としてできること、規約としてできること、利用者が負う範囲。この 3 つはいまどう分かれていますか** |
| 人間の介入を残すべきですか | **止める権限をもうひとつ足せるとしたら、何を採り、何を捨てますか** |

最後の 2 つが要点。**「損失は誰が持つか」は個別の契約を即答させる形**なので答えられない。
**3 つに割ると答えられて、しかも「どこが空いているか」がそのまま出る。**
「何を捨てますか」を付けると、足す話だけで終わらず、その会社の優先順位が出る。

---

## 二択にしない

「A ですか、B ですか」は、**どちらも必要な場合に「両方です」で終わる。**
実際そうなので、登壇者は正しい。**選べない質問を投げている側の設計ミス。**

3 択にするか、「最初に来るのはどれですか」と順番を聞くか、
**具体的な出来事をひとつ挙げさせる**。

同じ理由で「技術で解くか、契約で解くか」もやめる。
**「技術としては何を操作することになりますか」**なら手が動く答えになる。

---

## 場面を限定する

限定しないと「場合によります」で終わる。**登壇者が悪いのではなく、範囲が広すぎる。**

```
✗ エージェントが誤送金したとき、どうなりますか。
✓ Kova のような仕組みが x402 で JPYC を払った。そのあと商品が届かなかった。
  この場合に限って伺います。止められるのは、どこですか。
```

限定するには一次情報が要る。次項。

## 裏取りの失敗例

**製品名・数値・規制名を質問に入れるなら、入れる前に一次情報に当たる。**
台本は声に出すので、誤りは登壇者の目の前で露見する。

実際に起きたもの。

- **規制の年と対象を間違えた。**「人間のお客様には 2010 年から義務」と書いた。
  正しくは 2010 年採択・**2011 年から適用**で、対象は「人間の顧客」一般ではなく
  **マーケットアクセスを提供するブローカー・ディーラー**。
  証券会社の登壇者がいる部屋で読み上げるところだった
- **仕組みの説明を単純化しすぎた。**チャージバックを「消費者が申し立てれば戻る」と書いた。
  実際はカード会社と加盟店の証拠確認を挟む紛争処理で、資金は加盟店側から戻る。
  単純化すると、**別の技術にも同じ機能が作れるという誤解**を招く
- **前提が事実でなかった。**「分散型取引所の板に入ると」と書いたが、AMM 型には板がない。
  そのまま聞くと、登壇者の訂正から始まる
- **製品の帰属を確認せずに名前を出しかけた。**レビュアーが提案してきた製品名を、
  一次情報（公式の事例ページ）で開発元を確認してから採用した。
  結果は正しかったが、**確認せずに入れていたら、本人の目の前で他社製品と取り違えていた**

**仕様の「できないこと」は、そのまま質問になる。**

ERC-8004 の仕様には「advertised capabilities が機能し、悪意がないことは暗号学的に保証できない」と
書いてある。**これは仕様が自分で認めている限界**なので、作った本人に聞いても角が立たないし、
一般論で逃げられない。

```
> ERC-8004 には identity、reputation、validation の 3 つのレジストリがあります。
> 仕様自身が、こう書いています。advertised capabilities が機能し、悪意がないことは保証できない、と。
> では——エージェントに動かせる前に、レジストリの外でまだ必要な確認は何ですか。
```

**規格の原文を読むと、この種の一文が必ず見つかる。**探しに行く価値がある。

チェック手順。

1. 数値・年・固有名詞に印を付ける
2. **一次情報**（公式サイト、規制当局の原文、公開リポジトリ）で 1 件ずつ確認する
3. 確認できないものは**台本から外し、prep note に「★出典未確認」として残す**
4. 口に出さない数字は確認しなくてよい。**口に出すものだけ**
5. **「Y はできない」と断定する前に、規格の既定値と例外を見る。**
   x402 について「返金は決まっていない」と書いたが、正しくは
   **既定の `exact` スキームが不可逆**で、`batch-settlement` スキームには
   協調的な返金が定義されている。**スキーム名まで言うと、鋭さは落ちずに正確になる**

## 割れなかったときの逃げ

第 2 ラウンドは「答えが割れる」前提で作るが、割れないことがある。**その場の逃げを用意しておく。**

```
> では、◯◯ が決まらないまま進まないように、御社が置いているゲートは何ですか。
> そこで誰が何を確認しますか。
```

**顧客や他社の不備を挙げさせる形にしない。**守秘に触れるし、答えても角が立つ。

---

## 流れが止まったときの 2 問

どのセッションでも使える。**沈黙を待たない。**

```
> 公開されている事例をひとつ挙げてください。
> それを見て、御社が変えた判断は何ですか。

> 今日ここにいる方が、明日から手をつけるとします。
> 経営の側で決めることがひとつ。技術の側で確かめることがひとつ。
> それぞれ、何になりますか。
```

2 問目は**客席の職掌構成に合わせる。**片方だけに答えると、もう片方が持ち帰れない。

**「いちばん危ないと感じているものは何ですか」は使わない。**
事故や脆弱性の開示を誘発する。上場企業と金融は答えられないし、答えたら問題になる。
